# Repository review and prioritized punchlist — 2026-09-06

Reviewed baseline: `d8bc951`; working tree was clean. This is a review, not a fix release.

## Assessment

The repository has a useful, focused foundation: a query-only broker boundary, watchlist-only scanning, explicit presets, persisted runs, and substantial offline tests. Keep those. A rewrite or broader ticker discovery would be poor use of effort.

The biggest remaining weakness is **consistency between individually tested components**. Cached decisions can survive changed inputs; the position-scoring adapter omits inputs its exit rules require; journal inference expects a different symbol shape from the snapshot builder; and different dashboard panels observe different refresh states. Green unit tests currently do not establish that the complete daily workflow is correct.

The second weakness is **outcome measurement**. The growth target moves as NAV grows, histories mix accounts, and unknown trade outcomes become numerical performance statistics. The dashboard cannot yet reliably answer whether the strategy is progressing toward its stated goal.

This report covers actionable findings from a repository-wide inspection, not a guarantee that every defect has been found. Priority reflects software correctness and user trust, not a forecast of investment returns.

## Correctness and product-contract punchlist

P1 = address before relying on the affected decision/metric. P2 = next reliability pass. P3 = useful cleanup. Items marked **reproduced** have direct probe evidence; others follow from inspected call paths.

- [x] **C01 — P1: Recompute decisions against the current preset and portfolio.** `api/services/recommendations.py:200,227,836`. The five-minute cache stores already scored candidates under `(ticker, cash // 1000)`. Preset switching leaves it intact, and cache hits bypass scoring. **Reproduced:** cached quantity/eligibility survived a switch to Conservative and a cash change from $19,999 to $19,001. Cache broker evidence separately; recompute qualification, capacity, quantities, and eligibility for every run. Verify preset changes, cash crossing a contract-affordability boundary within one bucket, new reservations, and market-open transitions.

- [x] **C02 — P1: Wire entry credit and earnings timing into position exits.** `api/services/portfolio_scoring.py:83,102`; `core/position_scorer.py:113`. `score_position` omits `avg_cost` from `pos_data` and never supplies `earnings_info`. **Reproduced:** neither reaches the exit scorer. Profit-taking and earnings-in-window rules therefore cannot evaluate their intended inputs on this route. Forward validated broker entry cost and the earnings service's actual timing/provenance; verify at the route/service boundary, not just `evaluate_exit` in isolation.

- [x] **C03 — P1: Enforce current copy eligibility at the point of use.** `frontend/static/js/dashboard/top-recommendations.js:277,479,499,1388`; `core/run_model.py:49`. Copy depends on a captured candidate flag and positive quantity, independent of current run coverage/status. A nontradeable run becomes a staged ticket even when it is partial or stale during an open session. Read-time recomputation changes the run flag but leaves candidate flags untouched; the card polls only every five minutes. Gate live copy on current complete coverage and broker evidence, and allow staging only for the explicitly supported closed-market state. Revalidate the current run/candidate before writing the clipboard. Test aging, partial coverage, failure with last-good data, and market transitions using fake time.

- [x] **C04 — P1: Isolate history and journal data by account/environment.** `db/portfolio_snapshots_repository.py:57,76`; `core/wheel_runner.py:331`; `db/trade_events_repository.py:106`. Latest/history queries lack account predicates and journal analytics aggregate every event. **Reproduced:** one series contained SIMULATE and REAL snapshots. A restart with another account can distort pace and infer trades between unrelated books. Require `(env, opaque_account_id)` on history/baseline/analytics reads and persist that identity on events. Quarantine unidentifiable legacy events instead of assigning them to the active account. Test paper-to-real and real-account switches; review latest-run selection under the same identity boundary.

- [x] **C05 — P1: Preserve unknown trade outcomes as unknown.** `core/position_diff.py:71,151`; `db/trade_events_repository.py:122`. Inferred exits have `pnl=0`, but analytics count them in the win-rate denominator. Inferred entries also assign the current option mark to `premium_in`, despite the module promising unknown fill prices. **Reproduced:** an unknown exit produced one measured exit and a 0% win rate. Use nullable amounts plus explicit inferred/verified provenance. Exclude unknown outcomes from performance statistics and show their count separately. Test unknown, break-even, winning, and losing outcomes independently.

- [x] **C06 — P1: Align snapshot identity with trade-event inference.** `core/portfolio_snapshot.py:37,62`; `core/position_diff.py:92,112,132`. The builder preserves an option code as `symbol`; inference assumes `symbol` is the underlying. **Reproduced with builder-produced snapshots:** a roll became separate exit/entry events; a put disappearance plus 100 underlying shares became an exit rather than assignment. Store distinct underlying and contract identities, then group by underlying/type while retaining full contract keys. Add builder-to-inference integration tests with broker-shaped codes. Existing isolated fixtures hide this mismatch.

- [x] **C07 — P1: Use one durable growth baseline and target.** `core/growth_mode.py:46,49,63,68`; `frontend/static/js/dashboard/growth-panel.js:137`. Progress uses the first snapshot, while target/ETA use current NAV multiplied by five. **Reproduced:** $10k becoming $50k reports 100% progress but raises the target to $250k and still estimates another year. Persist a baseline per account, derive every goal metric from it, return reached status/zero remaining gap at the goal, and render server values. Keep the baseline independent of chart limits and retention pruning. Tests must pin one goal across refreshes, retention, and different history limits.

- [x] **C08 — P1: Make growth math finite and honest about its observation window.** `core/growth_mode.py:62,66`. **Reproduced:** a 1% NAV increase across one minute throws `OverflowError`, causing the history route to return 500. Flat/declining accounts return unknown annualized pace, making the UI say it is collecting data rather than reporting an observed decline. Require an adequate observation window, calculate safely, reject nonfinite inputs/results, and distinguish insufficient history from flat/negative performance. Test close timestamps, zero/negative NAV, declines, and large ratios. Until deposits/withdrawals are accounted for, label this as NAV change rather than strategy return.

- [x] **C09 — P1: Do not show missing marks as full profit.** `frontend/static/js/dashboard/dashboard-init.js:200,205`; `api/services/portfolio_scoring.py:81`. **Reproduced:** entry $2, one short contract, missing mark rendered `+100% $200`; `days_to_earnings=0` disappeared because `|| null` treats zero as missing. Preserve null/validity information through backend and UI. Unknown marks must suppress P&L and profit-taking calculations; use nullish handling for earnings today. Cover missing, invalid, legitimate zero, stale marks, and day-zero earnings.

- [x] **C10 — P2: Publish refresh completion to every affected panel.** `frontend/static/js/dashboard/run-strip.js:84`; `frontend/static/js/dashboard/top-recommendations.js:1293,1388`; `frontend/static/js/dashboard/dashboard-init.js:109`. The operational refresh starts a run but does not notify cards or growth panels when it completes. Cards can show an old snapshot until their five-minute poll; growth refresh listens for `#refresh-all-btn`, which no template emits. Have one bounded run-state poll notify panels when `run_id` changes. Refresh account, cards, positions, growth, and pace consistently without initiating another broker scan. Verify exactly one refresh request and prompt adoption of the completed run.

- [x] **C11 — P2: Show failed refreshes and distinguish fetch age from broker quote age.** `frontend/static/js/dashboard/run-strip.js:33,45,72`; `frontend/static/js/dashboard/top-recommendations.js:159`. With a last-good snapshot, the run strip ignores `attempt.state=failed`; non-OK requests return silently. It also labels fetch timestamp age as quote age. Retain last-good results but visibly show the failed/latest attempt and communication failure. Display broker update time and UTC fetch time separately, with explicit last-session labels. Verify failure-after-success, disconnected API, stale broker time with recent fetch, and recovery.

- [x] **C12 — P2: Make portfolio/event persistence recoverable.** `core/wheel_runner.py:182,189,331,339,346`. The run is published, then portfolio history is saved, then events commit individually. If an event write fails, the new baseline remains saved and the next run no longer reconstructs the missing transition. Use a shared transaction for the portfolio baseline plus its event batch, or a durable retryable derivation record keyed by run. Keep shortlist availability separate if desired, but expose journal failure. Test failure on the second event and retry without duplication or loss.

- [x] **C13 — P2: Use US market dates for position DTE.** `api/services/portfolio_scoring.py:75`. Position DTE uses the Windows machine's local date. In Brisbane, the calendar date can be one day ahead of the US session, advancing roll/expiry thresholds. Use the existing US market clock in `core/utils.py`. Verify identical results for Brisbane and New York hosts at the same instant, including DST and the expiry session.

- [x] **C14 — P2: Treat roll and assignment inference as uncertain without fills.** `core/position_diff.py:112,132`. Even after C06, arbitrary same-underlying disappeared/appeared legs are zipped into rolls, and any share increase is enough to infer put assignment. Separate buys and closes can produce the same snapshots. Preserve quantities, require compatible transitions, and label ambiguous cases as inferred rather than confirmed. Test multiple expiries, mismatched quantities, partial changes, and independent stock purchases. Broker fill reconciliation belongs in the outcome workstream below.

## Standards, security, and removal punchlist

These findings are separate from the product-contract findings. Cleanup proposals are judgments, not claims that small wrappers or large files are inherently wrong.

- [x] **S01 — P1: Enforce the loopback HTTP trust boundary.** `api/__init__.py:122,177`; `api/routes/run.py:42`. No-CORS does not reject cross-origin requests. **Reproduced with the route and a stubbed worker:** a form POST carrying `Origin: https://untrusted.example` received 202. Add explicit allowed-host validation and same-origin/CSRF protection for state-changing routes, preserving deliberate local clients. Test disallowed Origin, invalid Host, allowed browser requests, and the chosen nonbrowser client policy. ## The next two highest-ROI actions

### 1. Make a refresh produce one trustworthy decision screen

**Why first:** This directly improves the reason the project exists: open the app, get a reliable shortlist quickly, and understand what can be copied for manual review. It repairs decision correctness and feedback delay without expanding scope.

**Deliver:** C01–C03, C09–C11, C13; include S01/S02 as the small security boundary repairs and S03's explicit actionability table. Cache raw broker evidence rather than finished decisions. Recompute under an immutable set of run inputs. Pass full exit-rule inputs. Have the UI observe one completed run and revalidate copying against current evidence. Keep the existing query-only broker implementation.

**Acceptance:**

- Changing preset, cash, reservations, or market state never reuses an incompatible scored decision.
- Adapter-level tests prove entry credit and earnings reach exit rules.
- A stale/partial open-session run cannot produce a live or staged copy; the supported closed-session path is explicitly labelled and separately tested.
- One refresh starts one worker; visible panels adopt its completed run within one polling interval, targeted at five seconds or less.
- No missing mark produces a profit number; failure-after-success remains visible alongside last-good data.
- Measure cold and warm scan duration, broker request counts, coverage, and rejection reasons for the actual watchlist. Establish a repeatable baseline before promising a scan-time target or adding more caching.

**Effort:** roughly 3–5 focused engineering days, plus one live Windows/OpenD smoke session. This is an estimate, not a measured delivery promise.

### 2. Make the journal and 5x progress measure reality

**Why second:** Without trustworthy outcomes the user cannot tell whether the shortlist is useful or tune it responsibly. More scoring factors would add complexity to an unmeasured process.

**Deliver:** C04–C08, C12, C14 and S04. Start with account isolation, correct underlying/contract identities, unknown-outcome handling, durable goal baseline, safe growth math, and retryable event persistence. Then reconcile inferred transitions with available read-only Moomoo fill/history evidence. Keep quantities, costs, fees, account, contract identity, and provenance explicit; unavailable historical facts remain unknown. Track deposits/withdrawals separately from trading results before calling NAV growth strategy performance.

**Acceptance:**

- Paper and real accounts never share baselines, journal outcomes, or performance series.
- Broker-shaped snapshot transitions correctly identify compatible rolls/assignments and flag ambiguity.
- Unknown P&L is excluded from win rate; no mark is presented as an executed premium.
- A $10k baseline retains its $50k target when current NAV reaches $20k or $50k; retention and chart limits do not move it.
- Closely spaced runs, declines, cash transfers, failed event writes, and retries produce honest, finite, recoverable results.
- Before changing ranking parameters, compare observed outcomes by existing preset/tier with sample counts and limitations. Do not claim statistical edge from a handful of trades.

**Effort:** roughly 4–7 focused engineering days for the correctness foundation; broker-history reconciliation requires a separate estimate after verifying the account's accessible history and field semantics.
