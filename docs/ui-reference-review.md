# UI reference review

Reviewed 2026-10-11 for the local, signals-only Moomoo dashboard. These are transferable interaction and information-hierarchy ideas; the cited pages are UI/component references, not evidence about brokerage workflows. The implementation uses numbered areas, grouped native-anchor navigation, independent disclosures, and stage/elapsed feedback; stage-weight percentages were removed after this review.

## What the references show

- **Beautiful UI** groups examples by named component, including sidebar navigation, insight cards, filter/records tables, and task rows. Its loading example includes elapsed time; task rows distinguish running, failed, and completed work and show counts/details. Its expandable thinking traces expose deeper steps on demand. [Beautiful UI](https://www.beautifului.dev/)
- **beUI** presents composable cards with headers, descriptions, content and footers; it also lists status bars, collapsibles, tabs, and keyboard-controlled components. Some listed controls explicitly support reduced motion. [beUI](https://beui.dev/)
- **Rare UI** organizes its collection around individually named components and examples, with a quick-start path. This supports browsing by recognizable pattern, though the examples are primarily animated React components. [Rare UI](https://www.rareui.com/)
- **Transitions.dev** labels each motion example by its state change, including tab indicator movement, status-text swaps, and skeleton-to-content reveal. [Transitions.dev](https://transitions.dev/)
- **shadcn/ui**’s dashboard example groups navigation under headings and pairs metric labels with values and change indicators. Its table docs call the table responsive and describe sorting, filtering, visibility, selection, and pagination as behaviors to opt into for the specific table. The project describes its components as composable and accessible. [Dashboard example](https://ui.shadcn.com/), [table](https://ui.shadcn.com/docs/components/base/table), [data-table guide](https://ui.shadcn.com/docs/components/aria/data-table)

The apex `https://beautifului.dev` did not load through the text reader; the canonical `https://www.beautifului.dev/` page was accessible and reviewed. The other four cited sites loaded. Findings above are from the page content, not a pixel-level or keyboard audit.

## Transfer to this dashboard

- **Strengthen section boundaries** with the existing zero-radius, rule-based system: give each major panel a clear heading, short purpose line where needed, and consistent top/bottom rule. Use whitespace and hierarchy to distinguish primary signals from operational status and secondary analytics. This adapts the references’ named component groups and sectioned dashboard navigation to this app; it does not call for copying their styling.
- **Make navigation state unmistakable.** Keep section labels visible and use a persistent active marker plus text/shape/contrast, not color alone. Preserve a clear keyboard focus ring. The references show grouped sidebar navigation and active-tab indicators; choosing a stable active marker is a local recommendation. [Beautiful UI](https://www.beautifului.dev/), [Transitions.dev](https://transitions.dev/)
- **Replace progress that appears frozen with truthful activity context.** Show the current server-provided stage, elapsed time, and completed/total count when available. Show a numeric percentage only when the backend’s progress value is determinate and advances meaningfully; otherwise use an indeterminate activity indicator and stage text. If there is evidence of a failed or stalled attempt, label it and show the last update/next step. Do not invent counts or imply a completed fraction. This follows the loading-time and task-count examples above. Before this change, `run-strip.js` rendered the stage-weight `attempt.progress` as a percentage. It now shows the active stage and elapsed time; snapshot coverage remains the completed-run coverage count. [Beautiful UI](https://www.beautifului.dev/), [Transitions.dev](https://transitions.dev/), [local run strip](../frontend/static/js/dashboard/run-strip.js)
- **Make the key numbers recognizable.** Use a small, consistent metric treatment: sentence-case label, prominent value, and subordinate unit/change/context. Keep executable return visually primary and source, freshness, and risk context attached to the related signal. The dashboard examples demonstrate label/value/change grouping; the ranking and prominence choices here are local inferences constrained by the app’s scoring contract. [shadcn/ui dashboard](https://ui.shadcn.com/)
- **Use disclosure for supporting detail.** Keep the shortlist and decision-critical warnings visible; let users expand diagnostics and secondary analytics with a clearly named control and state. For option tables, preserve aligned numeric columns and a stable header; on narrow screens, keep the existing responsive wrapper and make horizontal overflow obvious rather than compressing values into unreadable text. Add sorting/filtering only where it solves a real review task. These are recommendations based on the references’ expandable traces and table examples, not claims that any reference was tested at 320 px. [Beautiful UI](https://www.beautifului.dev/), [shadcn/ui table](https://ui.shadcn.com/docs/components/base/table), [data-table guide](https://ui.shadcn.com/docs/components/aria/data-table)
- **Check both target widths and input modes.** Validate the dashboard at 320 px and 1440 px, with keyboard-only navigation, visible focus, and reduced motion enabled. Keep motion short and functional (for example, disclosure reveal or status change); avoid decorative number rolling or spring effects on scan data. The reference pages describe responsive tables, keyboard support, and reduced-motion variants, but do not establish that this app meets those checks. [shadcn/ui table](https://ui.shadcn.com/docs/components/base/table), [beUI](https://beui.dev/)
